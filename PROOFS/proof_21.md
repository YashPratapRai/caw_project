Title: Short Code Collision Resilience — Transparent Retry on P2002
Demonstrated: When two concurrent requests generate the same 8-character code, the unique constraint violation (Prisma P2002) triggers a silent retry with a new random code. The client never sees the collision.
Technical detail: generateShortCode() uses crypto.randomBytes(8).toString('base64url').slice(0,8) — 64^8 = 281 trillion possible codes, making collisions near-impossible but not zero. On P2002, the catch block calls continue (up to 5 retries). After 5 failures, the service returns HTTP 500 with an explicit retry instruction to the client.
Proof: Mocked collision on attempts 1–4 → attempt 5 succeeds → client receives HTTP 201 with a valid short link. Five consecutive collisions → HTTP 500 {"error":"Unable to generate a unique short code. Retry the request."}
Reasoning: Sequential counters leak information — code "1000" tells an attacker there are 999 other links, and code "1001" is predictable. Random codes eliminate enumeration. The retry loop absorbs the vanishingly rare collision without adding pre-allocation complexity. The database's unique constraint is the source of truth; the application retry is a UX optimization. GitHub uses the same random-then-retry pattern for gist IDs and commit short SHAs.
