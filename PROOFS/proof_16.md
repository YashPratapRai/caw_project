Title: Automatic Secret Redaction — Preventing Credential Leaks in Log Pipelines
Demonstrated: StructuredLoggerService strips sensitive values from every log entry before it reaches stdout. No developer action required — redaction is structural, not opt-in.
Technical detail: redact() walks metadata objects and arrays recursively. Any key whose lowercase form contains 'authorization', 'x-api-key', 'cookie', 'password', 'token', or 'secret' has its value replaced with '[REDACTED]'. Uses includes() (substring match), so 'x-api-key-v2', 'jwt_token', and 'client_secret' are all caught without maintaining an exact-match registry.
Proof: Log entry: {"x-api-key":"[REDACTED]","authorization":"[REDACTED]","content-type":"application/json"}. Original API key value never appears in stdout, stderr, or any log file.
Reasoning: Log aggregators (ELK, Datadog, Splunk) are breached more often than production databases because they have weaker access controls and longer retention. One plaintext API key in a log entry gives an attacker full tenant access. Opt-in redaction (where developers must remember to scrub) fails at scale — a single missed log.info(request.headers) leaks everything. Structural redaction at the logger layer eliminates this entire class of incident. Stripe uses the same approach: secrets are redacted at the serialization boundary, not at the call site.
