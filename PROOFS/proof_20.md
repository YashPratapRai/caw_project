Title: Database Timeout — Preventing Cascading Connection Pool Exhaustion
Demonstrated: Every Prisma query races against a configurable timeout (DB_TIMEOUT_MS, default 2500ms). Slow queries return HTTP 504 immediately; the server remains responsive for all other traffic.
Technical detail: LinksService.withDbTimeout() wraps each query in Promise.race: the Prisma promise vs a setTimeout that rejects with GatewayTimeoutException. The timer calls unref() so it does not block Node.js graceful shutdown — without unref(), pending timeouts would keep the process alive during SIGTERM handling.
Proof: DB_TIMEOUT_MS=100 + simulated lock contention → HTTP 504 {"error":"Database operation timed out during create link.","request_id":"d4e5f6a7...","status":504}. Concurrent GET /health returns 200 — the server is not blocked.
Reasoning: Without this timeout, one locked row in PostgreSQL holds a connection indefinitely. With a default pool of 10 connections, 10 slow queries saturate the pool and every subsequent request queues behind them. The entire service goes down because of one slow table. Failing fast at 2500ms releases the connection back to the pool and returns a clear 504 to the caller, preserving throughput for healthy queries. AWS RDS Proxy enforces the same pattern at the infrastructure layer.
