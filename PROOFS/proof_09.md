Title: Per-Tenant Rate Limiting — Correct Throttle Granularity for API Key Auth
Demonstrated: POST /links enforces 10 requests/60s per authenticated principal_id, not per IP. One tenant hitting the limit does not affect any other tenant.
Technical detail: CreateLinkRateLimitGuard keys the rate limit bucket as `create:${principalId}`. RateLimitService uses a fixed-window counter in a Map<string, {count, resetAt}>. On violation, the guard throws HTTP 429 with a structured error body containing code RATE_LIMIT_EXCEEDED — machine-readable, distinct from other 4xx errors.
Proof: Tenant "user1" sends requests 1–10 → all return HTTP 201. Request 11 → HTTP 429 {"error":{"code":"RATE_LIMIT_EXCEEDED","message":"Too many link creation requests"}}. Tenant "user2" sends request 1 concurrently → HTTP 201. Isolation confirmed.
Reasoning: Per-IP limiting is wrong for API key auth. One tenant deploys from 50 CI servers (50 IPs, each under limit, total far exceeds intent). Another tenant shares a corporate NAT with 200 employees (1 IP, legitimate users rate-limited by strangers). Per-principal_id eliminates both failure modes. The limit is configurable per deployment; high-volume tenants get higher limits via env var or future per-key config. Stripe, GitHub, and Twilio all rate-limit per API key, not per IP, for the same reasons.
