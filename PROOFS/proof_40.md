Title: Cache–Business Rule Alignment — Expired Links Never Served from Cache
Demonstrated: RedirectCacheService evicts entries the instant the link's expiresAt timestamp passes, even if the cache TTL (60s) has not elapsed. The cache never overrides a business rule.
Technical detail: get() evaluates two independent eviction predicates: (1) cachedAt + ttlMs <= now (cache staleness) and (2) expiresAt && expiresAt.getTime() <= now (link expiration). Either predicate triggers Map.delete(), increments the CACHE_MISS counter, and forces a fresh database lookup that will also fail with 404.
Proof: Link with expiresAt=T+30s, cached at T+0s (TTL=60s). T+29s: GET /r/:code → 302 CACHE_HIT. T+31s: GET /r/:code → cache evicts entry, DB lookup returns expired link → HTTP 404. No stale redirect served.
Reasoning: Without the expiresAt check, an expired link redirects for up to 60 more seconds from cache. If the link owner expired it because the destination was compromised (malware, phishing), that 60-second window exposes every visitor to the threat. The dual-predicate model treats the cache as a performance optimization that is subordinate to business correctness — the same principle behind HTTP Cache-Control: must-revalidate.
