Title: Tenant Isolation — Service-Layer Row Filtering, Not Controller-Layer
Demonstrated: Every Prisma query in LinksService appends `where: { createdBy }`. Cross-tenant access returns 404 — the resource appears nonexistent, leaking zero information about other tenants' data.
Technical detail: principal_id is extracted from x-api-key by ApiKeyGuard and attached to the request object. LinksService reads it and injects it into every findFirst, findMany, and delete call. The filtering is in the service, not the controller, so internal call paths (background jobs, admin tools, future controllers) inherit the same boundary automatically.
Proof: User1 creates link clx_abc. User2 (valid API key, different principal_id) calls GET /links/clx_abc → HTTP 404 {"error":"Link was not found.","status":404}. The link exists in the database but User2's query never matches it.
Reasoning: Controller-level auth checks are the #1 source of privilege escalation bugs in multi-tenant systems. A developer adds a new admin endpoint, forgets the guard, and suddenly one tenant can read another's data. Service-layer filtering makes this impossible — the WHERE clause is baked into every query regardless of the caller. This is the same isolation model Stripe uses for merchant data: the data layer enforces boundaries, not the routing layer.
